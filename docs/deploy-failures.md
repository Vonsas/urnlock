# 배포 실패 기록

배포(Vercel Production 빌드)가 실패하거나 '자동 배포가 반영되지 않았어요' 이슈가 열리면 여기에 남긴다.
새 실패는 맨 위 기록 표에 한 줄, 원인이 새로우면 아래에 절을 하나 추가한다.

## 로그 보는 법

- Vercel 대시보드 → urnlock(dldb) → Deployments → 실패한 배포 → Build Logs. `[dldb:health]` 줄이 배포를 멈춘 이유, `[dldb:api]` 줄이 실패한 요청.
- 실패한 배포 ID 는 GitHub 에서도 보인다 (로그인 필요 없음):
  `gh api "repos/Vonsas/dldb/deployments?environment=Production&per_page=20" --jq '.[].id'` →
  `gh api repos/Vonsas/dldb/deployments/<id>/statuses --jq '.[] | "\(.created_at) \(.state) \(.description)"'`
  - 설명에 `npx vercel inspect dpl_… --logs` 가 적혀 있다 (이 명령은 `npx vercel login` 후에만 됨).
- 자동 갱신(6시간마다)은 Deploy Hook 이라 같은 커밋의 배포 기록에 상태가 계속 쌓인다 - 목록의 마지막 줄만 보지 말 것.

## 2026-10-29 504 - 숙련자 요청이 API 시간 제한에 걸림

### 원인 (기초부터)

1. 티어 · 승률표의 숙련자 수치는 `min_hero_matches_total=80`(그 영웅 평생 80판) 필터로 받는다. 이 필터가 붙으면 deadlock-api 가
   미리 집계한 표(materialized view)를 못 쓰고 기간 안 모든 경기 + 플레이어마다 평생 판수를 다시 센다 (`hero_stats.rs` 의 `build_mv_query` 가 None).
2. deadlock-api 가 2026-10-20 평생 판수 세는 방식을 바꿨다 (`d133bfc` 'count hero experience without duplicates, per game mode').
   API 쪽 커밋 설명에도 이 요청은 쿼리 시간 제한 20초에 자주 걸린다고 적혀 있다 ('unranked or all-rank windows fail 80–100%', `44ccf34`).
   우리 실패도 10-21 부터 시작.
3. 빌드는 이런 숙련자 요청을 71개 보낸다 (기간 5개 × [전체 + 랭크 단계 11] + 일주일 전 11). 7 · 14 · 30일처럼 긴 기간일수록 무겁다.
4. 2026-10-26 부터 API 는 시간 제한에 걸린 쿼리를 10분 동안 바로 504 로 돌려보낸다 (`03e6bc1` fail fast). 우리 `load()` 는
   504 를 15초 · 30초 뒤 다시 요청했으므로 늘 같은 504 만 받았다 - 실패 한 건마다 약 1분씩 빌드만 늘었다.
5. 티어 단계 하나라도 빠지면 그 보드를 못 만들고, `health.json` 점검이 Vercel 빌드를 멈춘다 (의도된 안전장치 - 틀린 티어 대신 직전 배포 유지).

→ 결국 API 가 바쁜 시간에 갱신이 돌면 배포가 멈춘다. 한가한 시간엔 통과해서 '반복적으로 가끔' 실패하는 모양이 됐다.

### 확인한 것 (2026-10-29 16시 KST 전후, 로컬에서 직접 호출)

| 요청 | 결과 |
| --- | --- |
| 30일 · 전체 (숙련자 필터 없음) | 200, 0.5초 |
| 30일 · 전체 · 숙련자 | 504, 20초 |
| 14일 · 단계 7 · 숙련자 | 504, 21초 |
| 7일 · 단계 9 · 숙련자 | 200, 14초 (다른 때 504) |
| 같은 504 요청을 1분 뒤 다시 | 504, 0.5–0.8초 (10분 fail fast) |
| 1일 · 단계 7 / 단계 2 · 숙련자 | 200, 4.6초 / 6.4초 |
| 1일 · 전체 휘장 묶음(`bucket=avg_badge`) · 숙련자 | 504, 21초 |
| 1일 · 전령사+(71–116) 묶음 · 숙련자 | 200, 18초 (한계 근처) |

- 로컬 전체 빌드(`VERCEL=1`)로 재현: `tierk-7d-all-exp80` · `tierk-7d-s4…s9-exp80` 이 모두 `HTTP 504` - 7일 이상 숙련자 요청은 사실상 다 실패.
- 504 응답은 Cloudflare 의 `error code: 504` (Retry-After 없음).
- `hero_matches_total_buckets`(평생 판수 구간을 한 번에) · `bucket=avg_badge`(단계를 한 번에)도 같은 이유로 느리다 - 요청 수는 줄지만 한 요청이 20초를 넘는다.

### 이번에 고친 것

- `src/data/api/fetch.ts`: 504 는 재시도하지 않는다 (10분 fail fast 라 소용없음). 실패한 갱신이 20분 넘게 걸리던 것이 몇 분으로 줄고,
  바쁜 API 에 같은 무거운 요청을 세 번씩 보내지 않는다. 429 · 다른 5xx · 시간 초과는 그대로 재시도.
- 이것만으로 배포 실패가 사라지지는 않는다 - 숙련자 요청 자체가 바쁜 시간엔 20초를 넘기 때문. 그래서 아래처럼 구조를 바꿨다.


### 구조 변경 - 숙련자 수치를 조각으로 받아 쌓기 (2026-10-29, 결정)

- 조각: 랭크 단계별 전체 · 숙련자 수치를 하루(한국 0시) + 패치 경계 조각으로 받는다 (`src/data/api/tier-pieces.ts`). 판수 · 승수 · 킬은 더할 수 있어 기간 = 조각 합.
- 보관: 6시간마다 GitHub Actions 가 `tools/archive-tiers.ts` 로 받아 `src/data/tier-archive.json` 에 쌓고 커밋 → 그 푸시로 배포. 빌드는 더하기만 하고 파일에 없는 칸만 직접 받는다.
- 504 가 나면: 그 칸을 반으로 나눠 다시 묻는다 (하루 → 12 → 6시간) - API 는 같은 요청만 10분 거절하므로 나눈 요청은 바로 물을 수 있다. 그래도 못 받으면 예전 값을 두고 다음 실행에서.
- 늦게 들어오는 경기: 1시간 사이에 어제 경기 +1.1%, 사흘 전 +0.2% (2026-10-29 측정) → 끝난 지 3일 안 된 조각은 매번, 15일 안 된 조각은 하루 한 번 다시 받고 그 뒤 굳힌다.
- 기간 정의: '최근 7·14·30일' = n일 전 한국 0시부터 (7–8일). 현재 · 이전 패치는 패치 시각(정각 내림) 그대로.
- 일반 매치 숙련자 수치는 뺐다 (일반은 없어도 되고 랭크 숙련 수치는 꼭 있어야). 일반 매치는 1시간 조각도 붐비는 시간(한 시간 약 5,300판)엔 20.6초로 504.
  승률표 '전체(일반 포함)' 보기에서만 숙련 차이 열이 없다 - 승률 · 변화 · 픽률 · KDA · 판수는 그대로 (숙련자 필터 없는 요청은 0.5–2초).
- 검사: 티어 자동 검사의 직접 대조는 조각이 늦게 들어온 경기만큼 적을 수 있어 '많음'(겹침)은 엄격, '적음'은 넉넉하게 (`tier-check.ts`).
- 배포 확인 · 알림: 예전엔 갱신 작업이 배포 반영을 최대 20분 기다리며 Actions 무료 시간 대부분을 썼다 (10월 71번 668분, 비공개 저장소 월 2,000분).
  이제 Vercel 이 배포 결과를 GitHub 에 알리면 `health-notify.yml` 이 1분 안팎 돌아 이슈 + 디스코드(`DISCORD_WEBHOOK`)로 알린다.

첫 수집(조각 약 40개 × 단계 11개)은 숙련자 요청 하나에 10–20초라 1–2시간 걸린다. 이후 실행은 최근 조각만 다시 받는다.

검증 (2026-10-29, `tools/verify-tier-pieces.ts` · 로컬 전체 빌드):
- 휘장 묶음(`bucket=avg_badge`)으로 받은 단계 값 = 단계 범위를 직접 물은 값 - 단계 3 · 6 · 9 모두 정확히 같음 (둘 다 새로 받았을 때. API 캐시가 섞이면 늦게 들어온 경기만큼 다름)
- 최근 14일 전령사+ 조각 합 vs 직접: −0.085% · 숙련자 이틀 조각 합 vs 직접(단계 10): −0.13% - 조각을 받은 뒤 늦게 들어온 경기만큼 적음
